# Handover: who owns what, and how to keep the site running

For the PI, the co-owner and whoever maintains the site next. It covers R4 §9 and brief §F5: the owners, where each secret lives, the per-term editor routine, the scheduled rebuild, reverting, bumping Decap and Node, and campus contacts. First-time setup is `docs/SETUP-PRODUCTION.md`; editing content is `docs/EDITING.md`.

Labels: **DOCUMENTED** (primary source; R4/brief row given), **HYPOTHESIS**, **UNKNOWN**.

## 1. How the site works, in one paragraph

Content is Markdown/YAML in `content/` in one GitHub repository. Editors change it through Decap CMS at `/admin/`, which signs them in through a small Cloudflare Worker. **Every Save is a commit straight to `main`** ("Save goes live", DECISIONS D-17). Before it commits, the content manager runs the deploy's own checks in the browser: upload types and sizes, protected names, a conflict check, and the content validator on the whole site with and without the change. Each push to `main` triggers `deploy.yml`, which validates, builds a static site with Next.js on Linux and publishes it to GitHub Pages in about 2 minutes; the editor's status box follows that run. History and Recent changes in the editor read GitHub's API (GET only, D-19). The one exception is **Who can edit** in the editor's status box, where the owner (or a repository admin) invites and removes editors with a separately granted, tab-only GitHub permission (D-20, section 4). Maintainers' code changes still go through pull requests, which CI checks (`.github/workflows/ci.yml`). Nothing runs on a server except the sign-in Worker. There are no cookies, no analytics and no third-party requests on the public site.

## 4. Editors: the per-term routine

**Access is managed in the dashboard now (D-20).** The repository belongs to the **personal** GitHub account `bobalabx`. On a personal account only the owner can add or remove collaborators, and every collaborator can write (DOCUMENTED, GitHub REST "Collaborators"). The owner signs in at `/admin/` with `bobalabx` and uses **Who can edit** in the status box (`docs/EDITING.md` §17): invite by GitHub username, cancel an invitation, remove an editor. The first time after each page load, the panel asks for one extra GitHub permission (scope `repo`; the page keeps it only in memory, at most 8 hours, and forgets it on reload). GitHub itself keeps the grant until the account withdraws it at github.com → Settings → Applications → Authorized OAuth Apps (which also signs it out of the dashboard), and may add `repo` to the owner's later everyday sign-ins. Whether `repo` alone is enough to list the editors is checked by SETUP-PRODUCTION §H step 8: GitHub documents `read:org` as well, which the Worker would first have to allow. Everyone else sees whom to ask. github.com → repository → Settings → Collaborators still works the same way.

**Several admins: the organization option.** With a personal account, every invitation and removal needs whoever holds the `bobalabx` login. To let two or more people manage editors, move the site to a GitHub **organization** (free): either turn `bobalabx` into an organization or create one and transfer the repository to it (repository → Settings → Transfer). In an organization, its owners and the repository's **admins** manage collaborators (DOCUMENTED). Who can edit's code handles both: it reads `permissions.admin` and `owner.type` from GitHub, marks admins, sends invitations with write access ("push"), and leaves people who have access through the organization to the organization's own settings. **But its permission needs one change first:** for an organization's repository GitHub documents the `read:org` scope (and organization membership) for listing collaborators (DOCUMENTED). Add `read:org` to the Worker's scope allow-list (`providerScopes.github.allowed` in the fork's `src/index.js`) and redeploy the Worker, then set `access.scopes` to `["repo", "read:org"]` in `cms/source.mjs` and run `node scripts/cms/build-config.mjs` (in that order: SETUP-PRODUCTION §H step 8). Organization admins who are not members of the organization (outside collaborators with admin rights) may still be refused the list; they manage editors on github.com. Before such a move, also check the OAuth App's owner, the Worker's `ALLOWED_DOMAINS` and the Pages address (a transfer can change `<owner>.github.io`), update `backend.repo` in `cms/source.mjs` if the repository's full name changes, and repeat the SETUP §C6 smoke test. The rows below that mention the org, teams and `web-editors` describe that organization setup.

At the start of every term (and when anyone leaves):

- [ ] **Add** new editors: they create a GitHub account with 2FA and send the owner their GitHub username; the owner invites them under **Who can edit** (in an organization: also add them to `web-editors` if the lab uses teams); they accept GitHub's invitation email and sign in once at `/admin/`.
- [ ] **Remove** departing RAs under **Who can edit** (in an organization: remove them from the organization, not only from the team). Removing them ends their repository access, so a token left in their browser stops working (HYPOTHESIS: the OAuth grant itself stays until they revoke it; it no longer reaches the repo). Cancel invitations nobody accepted.
- [ ] Review **Who can edit**: the people who can save and the invitations still waiting (in an organization also Org → People: members, outside collaborators, and the 2FA column).
- [ ] Review `web-maintainers` (at least two people) and `.github/CODEOWNERS`.
- [ ] Check Org → Third-party access still lists only the lab's OAuth App.
- [ ] Check Actions → **Deploy** ran in the last few days (section 5) and that no `Broken external links` issue is waiting.
- [ ] Re-confirm consent for people listed on the site (H-11): `listed`, `photo_consent`, `email_public`, `now_at_public`.
- [ ] Skim Dependabot PRs and merge the green ones (section 9).

Per-person edit rights are not possible: everyone with edit access can edit every collection (brief critic list). The controls are the checks before every Save, the name on every save in History and Recent changes, and one-click Undo and Restore (D-17, D-19). Skim Recent changes (the editor's status box) once a term.

## 5. Deploys, the daily rebuild, and the 60-day trap

- **Push to `main`** (every Save in the editor) → `deploy.yml` → live in about 2 minutes (about 68 s from push to live, MEASURED on the live repository during the design round). The editor's status box reads the `deploy` job, not the whole run, so a later `record-slugs` failure does not hide a live save. Save-to-live time measured on the live site: ______ (fill in after the SETUP §C6 smoke test).
- **Daily rebuild at 11:17 UTC** (04:17 in Berkeley in summer). The site is static, so states that depend on today's date (upcoming talks, alumni by `end` date) change only when it is rebuilt. The rebuild is a full build; there is no ISR in a static export (DOCUMENTED, N-EXP via brief §F4). The minute is deliberately not :00, when GitHub delays or drops scheduled runs (DOCUMENTED, GH-SCHED).
- **GitHub disables scheduled workflows in a public repository after 60 days with no repository activity** (DOCUMENTED, GH-SCHED). A quiet summer can therefore freeze "Upcoming" and alumni states, and stop the weekly link check.
  - Notice it: Actions → Deploy shows a banner that the workflow was disabled, and the last run date stops moving.
  - **Re-enable:** Actions → Deploy → **Enable workflow** (and the same for "External links (weekly)"). With the GitHub CLI: `gh workflow enable deploy.yml` and `gh workflow enable links-weekly.yml`. Then **Run workflow** once.
  - Prevent it: any commit counts as activity, so a routine content edit resets the clock (HYPOTHESIS: GitHub counts commits as "repository activity"). Put a reminder in the lab calendar for mid-August.
  - Optional external trigger (brief critic list, HYPOTHESIS): a Cloudflare Worker cron (the lab already has the account) can call `POST /repos/<ORG>/<REPO>/actions/workflows/deploy.yml/dispatches` daily with a fine-grained token limited to Actions: write on this repository. It cannot run a workflow GitHub has already disabled, so it complements the reminder, it does not replace it.
- **Manual deploy:** Actions → Deploy → Run workflow (branch `main`).
- After each deploy the `record-slugs` job updates `content/.published-slugs.json` through a PR from `automation/published-slugs` (DECISIONS D-05). **Merge the first one only after editor v2 is live** (D-17): with the old rule, hiding a published entry would fail the deploy. After that, merge it when green. If it could not open the PR (setting in SETUP §B4), download the `published-slugs` artifact from the run, or run `npm run slugs:record` locally, and commit the file by PR.

## 6. Reverting

- **Content (normal):** in the editor, open the entry → **History** → **Undo this change** on the top row, or pick an older row → **Restore this version** (EDITING §8). It saves a new commit through the normal Save, with every check. Consent switches never come back on by themselves, and removed personal details only with an extra tick box (D-19). Restore acts on one file; revert a maintainer's multi-file commit by PR instead.
- **A save that breaks the deploy.** The editor cannot check everything the deploy does: an image the media step cannot process, or a build or export failure not caused by a content rule, still reaches `main` and stops every later deploy until it is fixed. The editor's banner names that save and who made it, later saves show "stuck on an earlier problem", and the fix is usually one click: open the entry and Undo (or Restore the previous version) in its History.
- **Code:** on github.com open the merged PR → **Revert** → this opens a new PR → wait for the checks → merge.
- **Emergency** (the live site is broken and a fix would take too long): Actions → Deploy → open the last good run → **Re-run all jobs**. A re-run builds the same commit as the original run (DOCUMENTED: re-runs use the original `GITHUB_SHA`). Two limits: GitHub only re-runs workflow runs up to 30 days old (DOCUMENTED, GitHub's "Re-running workflows and jobs" page), and the re-run's `record-slugs` job proposes that older commit's slug list, so close the `automation/published-slugs` PR it opens. The next push to `main` (any Save) deploys `main` again, so fix the cause right away.
- **Revert is not erasure.** The repository is public: every saved version, photos and emails included, stays readable on github.com after a restore. Removing personal data from history needs a history rewrite by a maintainer (and GitHub Support for cached views); an owner must lift the ruleset's "Block force pushes" for it, temporarily.
- Maintainers change code through pull requests. Editors' saves are direct commits to `main` by design: **never add "Require a pull request" or required status checks to `main`**, which would stop every Save (SETUP §B6).
- **Removing or renaming a published page:** add a `site.yml → redirects` entry (`from: /old/path/`, `to: /new/path/`). The validator demands one when a recorded slug disappears (`E_REDIRECT_MISSING`). A page that is only hidden (Visible on the website: No, that is `draft: true`; Listed or Profile page off) needs none: the validator only warns (`W_PUBLISHED_HIDDEN`, D-05 amendment). Prefer `status: archived` to deleting.

## 7. Bumping Decap CMS

Decap is vendored, not installed: the browser bundle sits in `public/admin/` with its SHA-256, and the pinned version is in **one file**, `cms/decap-cms.lock.json`.

1. Read the Decap release notes between the current and the new version (config or widget changes; `richtext` is still beta).
2. `node scripts/cms/vendor-decap.mjs --version X.Y.Z` (downloads with `npm pack`, verifies the registry integrity, copies `dist/decap-cms.js`, records the SHA-256 and the lock file).
3. `npm run test`: the CMS parity, vendoring and editor-v2 unit tests, including `tests/unit/cms/locale.test.ts`, which fails when a reworded locale key no longer exists in the bundle.
4. The editor's browser tests against `next dev` (each starts its own decap-server on a scratch copy of `content/`):
   - `npx playwright test tests/e2e/cms-local.spec.ts` re-measures the Decap work-arounds in `public/admin/cms-widgets.js` and `cms-start.js` (list item removal, keyboard reordering, the stale-editor reload) and the local demo end to end;
   - `npx playwright test tests/e2e/cms-save.spec.ts` checks one-click Save and the selectors it depends on: the Save dropdown (`[class*="ToolbarDropdown"]` holding `[class*="PublishButton"]`) and its first `[role="menuitem"]`, the double-click latch, the toast observer (`.Toastify__toast--error`, `--success`), the hidden header Media button (`nav [class*="AppHeaderNavList"] li > button[class*="AppHeaderButton"]`) and media-library Delete, the eye toggle (its `title` is the reworded `editor.editorInterface.togglePreview`), the panes (`[class*="StyledSplitPane"] > .Pane1`, `.Pane2`), `ControlErrorsList` and `ControlContainer` (with `label[for]`) for [Go to field] and for the "Not saved" band of a field in the wrong format (Decap 3.17.1 sends no toast for it), the hidden "Check for Preview" button (`[class*="PreviewButtonContainer"]`, `[class*="RefreshPreviewButton"]` in `admin.css`), and Decap's modal (`body.ReactModal__Body--open`, z-index 99999);
   - `npx playwright test tests/e2e/cms-live.spec.ts` checks the live column: one preview template per collection and per file (`site`, `home`, `join`, `about`, `accessibility`, `privacy`), the `CMS.editor` API (`getCurrentEntry`, `onEditorChange`, `applyFieldPatch`), History, Restore and Undo. **Undo right after a save depends on a Decap internal:** a save does not refresh Decap's `entries` store, so `cms-live.js` (`reopenAndRestore`) reopens the entry to finish the restore. `live.css` reserves 56 px on the right for Decap's eye and scroll-sync buttons.
   - Decap 3.17.1 leaves a persist promise's rejection unhandled after every refused save ("undefined" or "Object" in Chromium); the specs filter exactly that.
   - `npx playwright test tests/e2e/cms-access.spec.ts` checks Who can edit (D-20) with a routed GitHub and a fake sign-in Worker page; it does not depend on Decap internals beyond the local demo's Login, but run it after any change to the Worker fork or to `cms-dock.js`.
5. `npm run cms:local` and try an edit, a refused save and an Undo.
6. Open a PR; after merging, repeat the SETUP §C6 smoke test on the live `/admin/`.

**After any change to `public/admin/*.js`** (not only at a bump): Tailwind scans every project file for class names, admin scripts and Markdown included, so an exclamation mark directly before a word that is also a utility class (`hidden`, `visible`, `block`, …) adds an important-modifier rule to every public page's CSS (D-17). Run `npm run build` and check that the public CSS chunk in `out/_next/static/chunks/*.css` did not change, or avoid such spellings.

`node scripts/cms/vendor-decap.mjs --check` re-verifies the vendored file at any time. Re-evaluate Sveltia CMS (same config and files) around April 2027 (decision H-7).

## 8. Node.js version

- The version lives in `.nvmrc` (now `24.19.0`) and `package.json → engines` (`>=24.15 <25`, enforced by `.npmrc engine-strict`). All three workflows read `.nvmrc`.
- Node 24 is an LTS line (brief §F1). Bump the patch version by editing `.nvmrc` in a PR. Moving to the next LTS major means changing `.nvmrc` and `engines` together, running `npm ci` and the full suite, and checking that Next.js supports that Node major.

## 9. Dependencies

- Versions are pinned exactly (`.npmrc save-exact`); CI uses `npm ci`. `npm ci` prints exactly three `ERESOLVE overriding peer dependency` warnings (ESLint 10 vs eslint-config-next); that is expected. Do not use `--legacy-peer-deps`.
- **Security floor: never deploy `next` below 16.4.1** (brief §F1).
- Dependabot (`.github/dependabot.yml`) opens grouped PRs on Mondays for npm packages and for the SHA-pinned actions. Majors of Next, React, TypeScript (≥ 6.1) and `@types/node` are ignored on purpose: Next 17 makes Cache Components the default (H-13, revisit then), and `typescript-eslint` needs TypeScript < 6.1.
- A Dependabot PR is safe to merge when all CI jobs are green.

- **Full history for builds.** Each direction page's "Last updated" date is the newest commit that touched its own content files (`git log -1 -- <files>`, §D5.11). A shallow clone (`actions/checkout`'s default `fetch-depth: 1`) makes HEAD look like it added every file, so every direction page would show the date of the last commit of any kind. The `build` jobs in `deploy.yml` and `ci.yml` therefore check out with `fetch-depth: 0` and `filter: blob:none` (commits and trees only, still fast), and `deploy.yml` fails before building if the checkout is shallow. Keep both settings if you edit the workflows or move the build to another host; `tests/unit/wp8/workflows.test.ts` checks them.
- **The `record-slugs` job holds the only write-scoped token.** Its checkout sets `persist-credentials: false`, and it installs with `npm ci --ignore-scripts --omit=dev` because the slug script needs only `yaml`. The token goes to `git push` in the URL of the one step that pushes, so no dependency install script can read a stored token. `tests/unit/wp8/workflows.test.ts` checks this too.
- **JS baseline B** is in `docs/PERF-BASELINE.md` (measured on Windows). The `budgets` job prints the JS of the empty route on Linux and warns ("JS baseline drift") when it differs from B by more than 1 KB; then re-measure and update PERF-BASELINE.md by PR.
- Lighthouse is a pre-launch manual step: `node scripts/perf/lighthouse.mjs` (see `docs/QA-CHECKLIST.md` §6, including what to do while every direction is still a draft).

## 11. Windows notes (local builds only)

- The deployable site is always built by CI on Linux. A Windows `next build` writes the App Router's prefetch files into folders such as `out/kit/__next.kit/__PAGE__.txt` instead of `out/kit/__next.kit.__PAGE__.txt`, so client navigations get 404s and fall back to slower loads (MEASURED 2026-10-20 with Next 16.4.2; Next issue #85374; DECISIONS D-07). `npm run build` repairs this automatically on Windows (`scripts/fix-win-export.mjs`). Never upload a Windows-built `out/` by hand.
- The working tree may live in OneDrive (DECISIONS D-01). Never run two `next dev` / `next build` processes in it at once.

## 13. Why not move the site to Vercel Hobby or Netlify Free

- **Vercel Hobby** is for non-commercial personal use only, and only the owner's commits deploy (DOCUMENTED, R4 V26). A lab site is institutional and RAs commit through the CMS, so their changes would not deploy.
- **Netlify Free** pauses every site when the monthly credits run out (DOCUMENTED, R4 V27); about twenty production deploys a month would exhaust it.
- GitHub Pages is free for a public repo, needs no server, and has a 1 GB site / 100 GB-per-month soft bandwidth limit (DOCUMENTED, R4 V20). If the lab needs full-site draft previews or response headers (for example `frame-ancestors` for `/admin/`, which a `<meta>` CSP cannot set), Cloudflare Pages is the documented alternative (brief §F5, §G4).

## 14. Known limits

- Drafts and history are publicly readable on github.com in a public repo (D-06). Keep embargoed and personal data out of drafts.
- `/admin/` cannot get header-based clickjacking protection on GitHub Pages (`frame-ancestors` needs a header; brief §G4). `cms-start.js` therefore refuses to run inside a frame (a script guard; it does not protect against a browser with scripts off, where the CMS does not run anyway).
- The first CMS save of a content file re-writes it in Decap's YAML style (lines folded at 80 characters, date quotes dropped, keys in the editor's order, empty `social: {}` removed), so that pull request shows formatting-only lines next to the real change. Later saves of the same file show only the edit. Review with "Hide whitespace" off and read the changed values, or ask for the formatting to be split out.
- The editor's live column renders the real site from the editor's own data (D-18), but there is no deployed staging site (brief critic list): image variants, the build and the export run only in the deploy.
- Decap's own admin interface accessibility: UNKNOWN.
- **Editor v2 (D-17 to D-19):**
  - A sub-second race remains between the conflict check and Decap's commit. GitHub then refuses the second save (422), and the band says "someone else saved at the same moment … press Save again".
  - History is public: revert is not erasure (§6).
  - Restore brings back file names, not image bytes: a replaced or deleted upload cannot come back from History (a maintainer task).
