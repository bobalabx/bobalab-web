## Commands

```sh
node scripts/cms/build-config.mjs            # regenerate public/admin/* after changing cms/ or the schema
node scripts/cms/build-config.mjs --check    # CI-friendly: exit 1 if out of date (also a unit test)
node scripts/cms/vendor-decap.mjs            # (re)vendor decap-cms@<lock version> with npm pack, verify, record SHA-256
node scripts/cms/vendor-decap.mjs --check    # network: vendored file == npm tarball's dist/decap-cms.js
node scripts/cms/vendor-decap.mjs --version 3.17.2   # bump Decap, then run the tests below
npm run cms:local                            # local demo (decap-server :8081 + next dev :3100, no account)
node scripts/cms/check-backend.mjs [out/admin/config.yml]   # REPLACE-ME left in the backend: warning, error once site.yml launched: true
npx vitest run --config vitest.config.ts tests/unit/cms tests/unit/preview   # parity, config, hooks, editor v2, vendor
CMS_VENDOR_CHECK=1 npx vitest run --config vitest.config.ts tests/unit/cms   # + tarball check (network)
npx playwright test tests/e2e/cms-local.spec.ts tests/e2e/cms-save.spec.ts tests/e2e/cms-live.spec.ts   # editor end to end (needs next dev on :3100)
npx playwright test tests/e2e/cms-access.spec.ts   # Who can edit: routed api.github.com + a fake sign-in Worker page (decap-server on :8301)
```

## Production hookup

In `cms/source.mjs`, check `backend.base_url` (the sign-in Worker), `backend.repo` and `SITE_URL`, run the generator, open a PR. The CSP of `/admin/` is generated from `csp` in the same file. Saves are direct commits to `main` (`publish_mode: simple`, D-17), so `main` must never require a pull request or status checks (`docs/SETUP-PRODUCTION.md` §B6).

## Measured facts (2026-10-20, Chromium, decap-cms 3.17.1)

- **`'unsafe-eval'` is required** in `script-src`: Decap validates its config with Ajv, which compiles with `new Function`; without it Decap stops at "Error loading the CMS configuration" (the e2e spec re-measures this every run). `connect-src` also needs `blob:` (Decap fetches its own object URLs).
- **Richtext marked every entry as changed on open** (its load-time re-serialisation reaches Decap as a change). `cms-widgets.js` re-registers Decap's own control under the same name with a wrapper that drops changes made before the editor touches the field and maps the load-time form back to the stored text: entries now open with "Changes saved" (e2e: "rich-text bodies …"). A real edit still saves the widget's Markdown for the whole body (`-` → `*`, tight lists → loose lists); the `markdown` widget does not, see `docs/change-requests/WP6/3-…`. At a Decap bump, check whether the wrapper is still needed.
- **File/image widgets cannot carry a `pattern`**: a valid `https://` value fails Decap's pattern check and blocks saving, so these fields have none (the validator still checks them).
- Decap keeps cleared optional fields as `""`, which the schema rejects for URLs, dates and DOIs; `cms-hooks.js` removes them before saving.
- Only `dist/decap-cms.js` is vendored. Its lazy chunks (CodeMirror modes for the `code` widget, a WebP encoder for `media_processing`) are not used by this config; rich-text code blocks are turned off for that reason.
- Without manual init, a slow script download let Decap render its default preview before our templates registered (about 1 load in 10); `cms-start.js` fixes it.
- **Publication file names** (`{{fields.authors.0.name}}-{{year}}-{{slug | truncate(28)}}`): Decap templates cannot take a last name, so the first author's full name is used and `{{year}}` is the year the entry is created. The title part is cut at 28 characters so the PI's 26-character name still fits the 60-character limit of `SLUG_PATTERNS.publications`; `cms-hooks.js` re-computes the name Decap will give a new entry (any collection) and blocks the first save with advice when it would break the pattern or the length (validator `E_SLUG`), e.g. a longer first-author name. When the address fits but starts with a multi-word name, or the paper's year is not this year, the first save is held back once with advice (type the last name only); saving again keeps it.
- **Phone widths:** Decap 3.17.1 gives the editor and its top bar `min-width: 800px`, so the page scrolled sideways at 390 px and the account menu was off-screen. Below 800 px `admin.css` shows the form at full width (and hides the site link and "Check for preview" in the top bar); `cms-layout.js` adds an Edit / Preview & history switch, and in Edit mode the live column stays rendered off-screen so the site check keeps working.
- **Editor v2 (D-17 to D-19), measured in Decap 3.17.1:** Decap has no save API and no in-flight guard (a double click saved twice), so `cms-save.js` makes Save one click with a latch and falls back to Decap's two-click menu; preSave handlers chain, so `cms-save.js`, registered after `cms-hooks.js`, sees exactly the data Decap commits; postSave is awaited before "Saved" shows, so ours returns at once; Decap's same-name upload "replace" deleted the saved file at once, so the confirm is refused; a save does not refresh Decap's `entries` store, so Undo right after a save reopens the entry. Details and the selectors to re-check at a Decap bump: `docs/HANDOVER.md` §7.
- **Removing a Direction order item threw** (`Invalid keyPath: expected Ordered Collection or Array: ai-at-work`): Decap's `ListControl.handleRemove` calls `metadata.removeIn(<item value>)` for single-field lists that carry relation metadata. `cms-widgets.js` subclasses the list control and hides the metadata from that one call (e2e: "Direction order …"). Re-check at a Decap bump.
- **Lists cannot be reordered with the keyboard in Decap**: the list widget gives dnd-kit only mouse and touch sensors. The same subclass moves an item with the Up/Down arrow keys on its focused handle through Decap's own `onSortEnd`; `cms-a11y.js` names handles ("Reorder “ai-at-work”, item 2 of 4"), describes the keys and replaces the UUIDs in dnd-kit's spoken drag messages. Multi-select tags still reorder by mouse only (remove and re-add as the alternative).
- **The editor kept the previous entry when only the address changed** (after a save, a pasted entry link opened over the old form and Save wrote the old file). `cms-start.js` reloads the page when the address moves from one entry to a different existing one; `cms-hooks.js` refuses a save whose entry is not the one in the address.
- **"Visible on the website" (D-21).** Every `draft` field uses `widget: "visible"` (`cms/source.mjs` `VISIBLE`; the generator refuses it on any other field and refuses any other widget on a boolean). The file still stores `draft` (Yes = `draft: false`, No = `draft: true`), so the site, the validator, History's commits and the requiredRules (`{ field: "draft", notIn: [true] }`) are unchanged. The control is a `<button role="switch">` named by Decap's label, with `aria-checked` and a visible Yes/No word; it writes only booleans and only on a press, so opening an entry never marks it changed. Read in the 3.17.1 bundle: Decap's own boolean toggle keeps the value it mounted with (`useState(active)`), so a value set from outside (Restore, "Bring in their changes") would not redraw it (read in the code, not measured in the browser); ours draws `props.value` every time. History describes it as "Visible on the website: Yes → No". `cms-a11y.js` hides Decap's "(optional)" after its label (a Yes/No switch always has a value), so its name is exactly "Visible on the website". New entries start with Yes (`default: false`, D-17 open question 8). The collection lists mark hidden entries "· hidden" and offer the filter "Hidden from the website".
- **Retired publication statuses (D-21).** `cms-data.js` `legacy.publications.status` (generated from `scripts/content/migrate-status.mjs` `STATUS_MAP`) maps the statuses used before 2026-10-29 to today's; Restore and Undo of an older version use it (`buildRestorePatch` in `cms-live.js`), so the Status select never receives a value it does not offer.
- **Validator-only errors** (`E_AS_OF_MISSING`, `E_STATUS_SOURCE_MISSING`, `E_YEAR_MISSING`, `E_DIRECTIONS_EMPTY`, `E_DIR_ORDER_DUP`) are mirrored as `requiredRules` / `uniqueRules` in `cms/source.mjs`; `tests/unit/cms/hooks.test.ts` runs the validator on the same edits, so a change on one side fails the test until the other follows.
- **Colours**: previews receive Decap's `getCollection`; the direction preview lists the colours of the other live directions, and the second `preSave` listener refuses a colour already in use (the validator warns with `W_COLOR_DUP` before launch and fails with `E_COLOR_DUP` once `site.launched` is true).
- **/admin/ in a frame**: the CSP is a `<meta>` (GitHub Pages sends no headers), where `frame-ancestors` is ignored, so `cms-start.js` does not start Decap inside a frame and shows a link to open it on its own.

## Who can edit (D-20, maintainer notes)

- **Two tokens.** Decap's everyday sign-in keeps `auth_scope: public_repo` (localStorage `decap-cms-user`, read by `cms-github.js`, GET only). It cannot list or change collaborators, so `cms-access.js` asks the same Worker for a second token: `window.open(<base_url>/<auth_endpoint>?provider=github&site_id=<host>&scope=<scopes>)`, as Decap does (site_id = the host, `demo.decapcms.org` on localhost).
- **Scopes:** `access.scopes` in `cms/source.mjs` (→ `cms-data.js` `auth.scopes`), `["repo"]` today. GitHub documents **`read:org` and `repo`** for listing collaborators with an OAuth token (DOCUMENTED); whether `repo` alone works on the personal repository is a HYPOTHESIS until SETUP-PRODUCTION §H step 8 has been run. The Worker's allow-list (`providerScopes.github.allowed` in its `src/index.js`) is `repo`, `public_repo`, `user`, `read:user`, `user:email`: a request made only of those scopes is passed on as asked (a narrower one such as `public_repo` included), but **one scope outside the list makes the Worker quietly ask GitHub for its default `repo,user` instead**. So to add `read:org`: first add it to the Worker's allow-list and redeploy the Worker, then to `access.scopes`, then run `node scripts/cms/build-config.mjs`. In the wrong order, GitHub never gives `read:org` and the panel says "GitHub didn't give “read:org”" (it refuses any token whose `X-OAuth-Scopes` lacks a scope asked for). A 403 or 404 on the list for an admin whose token has every scope asked for shows the "GitHub didn't show who can edit" view (no loop back to Give permission).
- **Handshake** (the Worker's `outputHTML`): the popup posts `authorizing:github` to its opener with target `*`; the page answers `authorizing:github` to that popup only, addressed to the Worker origin; the Worker checks the page's origin against `ALLOWED_DOMAINS` and posts `authorization:github:success:{"provider":"github","token":"…"}` (or `:error:{"provider","error","errorCode"}`) to that origin. `cms-access.js` takes a message only when `event.origin` is exactly the Worker origin, `event.source` is the popup it opened, and (for the answer) the handshake came first. A closed popup is noticed by polling `popup.closed` every 0.5 s, with 0.6 s of grace for a last message; github.com's sign-in page sends no `Cross-Origin-Opener-Policy` (MEASURED 2026-10-26), so the opener keeps its handle. More than 10 minutes (the Worker's state cookie) gives up.
- **Decap's leftover listener.** Decap's `NetlifyAuthenticator` adds its `message` listener before opening its Login popup and removes it only after a handshake; it checks the origin, never the window. In a tab where that popup was closed or blocked, it would take our token and store it in localStorage `decap-cms-user`. `cms-access.js` therefore listens with `capture: true` (at the target, capturing listeners run first) and calls `stopImmediatePropagation()` on every message from a popup it opened; a token that Decap's stored user holds anyway is not used (backstop). Keep this in mind when upgrading Decap.
- **The token** is checked with `GET /user` (same login as Decap's user; `X-OAuth-Scopes` must include every scope asked for when present: api.github.com exposes that header to browsers, MEASURED), then kept **only in memory** (a variable inside the IIFE: no storage, not on `window`) for at most 8 hours. It is dropped on sign-out, another account and after 8 hours (2-second check), on a 401 and on "Turn it off now"; a reload or closing the tab drops it too. The page cannot revoke it at GitHub (OAuth App tokens do not expire; revoking needs the client secret): only the account can, under Settings → Applications → Authorized OAuth Apps, which also signs it out of the dashboard. `window.BobalabAccess` offers `open`, `forget`, `hasPermission` and `parseUsername`; the test hooks (`_request`, `_state`, …) exist only when `window.BOBALAB_TEST_HOOKS === true` before the script runs (the unit tests' sandbox).
- **Requests with it** are a fixed list (`rules()`): `GET /user`; `GET /repos/{repo}/collaborators?affiliation=all|direct&per_page=100&page=n`; `GET /repos/{repo}/invitations?per_page=100&page=n`; `PUT` and `DELETE /repos/{repo}/collaborators/{login}`; `DELETE /repos/{repo}/invitations/{id}`. Anything else, and a `PUT` or `DELETE` on the owner account's own login, is refused before `fetch` (unit tests "refuses any other request" and "never changes the owner account's own access").
- **Errors:** a 403, 422 or 429 with `Retry-After`, with `x-ratelimit-remaining: 0`, or with words such as "secondary rate limit", "abuse" or "spammed" is "busy" (it never drops the token). The 50-invitations-a-day answer is matched on a 422 that is busy, says "spammed" or mentions an invitation limit: HYPOTHESIS (D-20). Public profiles (`GET /users/{login}`, names and avatars) and the admin check (`GET /repos/{repo}` → `permissions.admin`, `owner.type`) go through `BobalabGitHub.get` with the everyday token.
- **Personal account vs organization:** on today's personal account only the owner is admin, the invitation's `permission` is ignored, and `PUT` answers 201 (invitation emailed) or 204 (already a collaborator). If the repository moves to an organization, `owner.type` is `Organization`: invitations send `{"permission":"push"}`, admins are marked, and people with access through the organization (not in `affiliation=direct`) have no Remove (manage them in the organization's settings).
- **Address of the Worker:** `cms-data.js` → `auth: {baseUrl, endpoint, adminUrl}`, generated from `backend.base_url`, `backend.auth_endpoint` and `SITE_URL` in `cms/source.mjs`. A new Worker address needs no change in `cms-access.js`.
- **Testing it** without GitHub: `tests/unit/cms/access.test.ts` (fake GitHub, fake popup and message events) and `tests/e2e/cms-access.spec.ts` (Playwright routes for `https://api.github.com/**` and the Worker origin; the fake Worker page answers only a trusted opener, like the real one). Never test it against the real repository: invitations email real people.
